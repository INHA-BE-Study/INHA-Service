# 미결정 항목 (Open Decisions)

아직 **결정되지 않은 항목**을 모은다.
**여기 있는 항목은 임의로 값을 정하지 않는다.** 관련 기능을 구현하기 전에 팀이 결정하고, 확정되면 본 문서와 관련 문서를 갱신한다.

- A. 서비스/정책 미결정 항목 — 기획 단계에서 보류된 항목
- B. 엔지니어링 정합성 결정 필요 — 문서 작성 중 코드와 기획서 비교에서 발견된 항목

---

## A. 서비스 / 정책 미결정 항목

| # | 항목 | 현재 옵션 | 결정이 필요한 이유 | 영향받는 컨텍스트 |
|---|---|---|---|---|
| A1 | **대학원생 포함 여부** | (가) 학부 재학생만 / (나) 대학원생 포함 | "재학생" 정의에 따라 가입 자격·졸업생 차단 로직·매칭 대상 풀이 달라진다 | Auth(가입/재학생 검증), Matching(대상 풀) |
| A2 | **매칭 실행 시각** | 저녁 **7시** / 저녁 **8시** | 18:01 요청 마감 후 일괄 매칭을 언제 돌릴지 — 스케줄러 cron, 결과 통지/알림 발송 시각이 확정돼야 구현 가능 | Matching(스케줄러), Chat(채팅방 생성 타이밍), 알림 |
| A3 | **활성 유저 기준 N일** | 최근 N일 이내 로그인 (N 미정) | 소프트 필터의 "활성 유저" 범위를 정함. N에 따라 매칭 후보 수가 달라지고, 로그인 시각(`lastLoginAt`) 기록이 필요해짐 | Matching(소프트 필터), Auth(로그인 시각 기록) |
| A4 | **프로필 사진 공개 여부** | (가) 비공개 / (나) 공개 / (다) 단계적 공개 | 공개 정책에 따라 사진 저장(S3) 도입 시점·비용, 프로필 노출 범위가 달라진다 | Profile, Matching(노출), 인프라(S3 비용) |
| A5 | **프로필 필수 입력 항목** | 현재 전부 선택 입력(MBTI/관심사/연애스타일/흡연·음주 등) → 일부 필수화 여부 | 필수 항목이 정해져야 가입/온보딩 플로우와 매칭 점수화에 쓸 최소 데이터가 보장됨 | Profile, Auth(가입 플로우), Matching(필터/점수화) |

## B. 엔지니어링 정합성 결정 필요

> 아래는 기획서 표기와 실제 레포 코드가 다른 부분이다. 문서는 **실제 코드**를 기준으로 작성했으나(→ [conventions.md](conventions.md) §9), 명칭을 어느 쪽으로 **통일**할지는 팀 결정 사항이다.

| # | 항목 | 현재 옵션 | 결정이 필요한 이유 | 영향받는 컨텍스트 |
|---|---|---|---|---|
| B1 | **베이스 패키지명** | `org.study.inhamatch`(실제) / `com.inha.dating`(기획 예시) | 패키지 리네임은 전 코드에 영향. 통일하지 않으면 문서·코드가 계속 어긋남 | 전체 |
| B2 | **공통 패키지명** | `global`(실제) / `common`(기획) | 공통 모듈 위치 명칭 통일 | 전체(global) |
| B3 | **매칭 폴더명** | `match`(실제) / `matching`(기획) | 패키지 경로 통일 | Matching |
| B4 | **계층 명칭 / dto** | `entity`(실제) / `domain`(기획) · `dto` 폴더 미생성 | 도메인 모델 계층 명칭 확정, DTO 폴더 신설 필요 | 전체 |
| B5 | **권한 enum명** | `Role`(실제) / `UserRole`(기획) | 보안 코드 전반에서 참조되는 타입명 통일 | Auth, 전체 |
| B6 | **프론트 언어/상태관리** | JavaScript(현재) / TypeScript + Zustand(목표) | 목표 스택(TS+Zustand) 전환 시점·범위 결정 | 프론트엔드 |
| B7 | ✅ **`User` 엔티티 필드 보강** | (해결됨) `grade`, `gender` 필드 추가 및 `completeSignup(grade, gender)`로 가입 완료 플로우 구현됨 (`User.java`) | ~~정책상 성별(필수 선택)·학년이 필요하나 엔티티에 없음~~ → 해결 | Auth, Matching |

> B 섹션은 코드 변경을 수반하므로 이번 "문서 셋업" 작업 범위 밖이다. 결정 후 별도 작업으로 정렬한다. (B7은 `feat/auth` 브랜치에서 이미 구현되어 해결됨으로 갱신)

## 결정 기록 방법

항목이 확정되면:
1. 본 문서에서 해당 행을 **"✅ 결정됨: <내용> (YYYY-MM-DD)"** 로 갱신(또는 하단 "결정 완료" 섹션으로 이동).
2. 영향받는 문서([service-policy.md](service-policy.md) / [domain-design.md](domain-design.md) / [architecture.md](architecture.md) / [conventions.md](conventions.md))를 함께 수정.
3. 그 다음에 구현을 진행한다.
