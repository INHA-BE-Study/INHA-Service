# 도메인 설계 (Domain Design)

바운디드 컨텍스트의 경계, 컨텍스트별 책임, 핵심 엔티티를 정의한다.
정책의 "무엇"은 [service-policy.md](service-policy.md)에, 여기서는 "어떻게 나누고 무엇을 소유하는가"를 다룬다.

---

## 1. 바운디드 컨텍스트 개요

| 컨텍스트 | 패키지(`org.study.inhamatch.domain.*`) | 한 줄 책임 |
|---|---|---|
| **Auth** | `auth` | 인증/인가 — 누가 우리 서비스를 쓸 수 있는가 |
| **Profile** | `profile` | 사용자 프로필 및 성향 정보 |
| **Matching** | `match` | 매칭 요청·필터링·일괄 매칭 |
| **Chat** | `chat` | 매칭된 두 사람의 실시간 채팅 |
| **Report** | `report` | 신고 및 차단 |
| (공통) | `global` *(domain 아님)* | 공통 설정·보안·예외·유틸 |

> 패키지 폴더명은 **`match`**(개념명 Matching), 공통은 **`global`**(개념명 common)이다.

---

## 2. 컨텍스트 맵 / 의존 규칙

- 컨텍스트 간 **직접 의존(엔티티/리포지토리 직접 참조)을 지양**한다.
- 경계를 넘는 참조는 **ID 기반**(예: `userId: Long`을 보관) 또는 **명시적 인터페이스**(서비스 포트)를 통한다.
- 모든 컨텍스트는 `global`(공통)에만 의존할 수 있다.

```
            ┌──────────────────────────────────────────┐
            │                  global                   │  ← 공통(설정/보안/예외/유틸)
            └──────────────────────────────────────────┘
               ▲        ▲        ▲        ▲        ▲
            ┌──┴──┐  ┌──┴───┐ ┌──┴───┐ ┌──┴──┐ ┌──┴───┐
            │Auth │  │Profile│ │Match │ │Chat │ │Report│
            └─────┘  └───────┘ └──────┘ └─────┘ └──────┘
```

대표적인 컨텍스트 간 관계(모두 **ID/이벤트/인터페이스** 경유, 직접 참조 아님):

| 출발 | 도착 | 관계 | 경유 방식 |
|---|---|---|---|
| Matching | Auth | 매칭 대상 사용자 식별 | `userId` |
| Matching | Profile | 공통 관심사 점수화 | 프로필 조회 인터페이스 / `userId` |
| Matching | Report | 차단 상대 제외(하드 필터) | 차단 목록 조회 인터페이스 |
| Chat | Matching | 매칭 확정 → 채팅방 생성 | 매칭 성립 결과/이벤트 |
| Report | Chat | 신고 시 채팅방 자동 나가기 | 채팅 종료 인터페이스/이벤트 |

> 위 관계의 구체적 구현(이벤트 발행 vs 직접 호출 인터페이스)은 구현 단계에서 컨텍스트 오너 간 협의로 정한다. 원칙은 "**경계를 넘는 참조는 ID 또는 명시적 인터페이스**"이다.

## 3. 컨텍스트별 책임 & 핵심 엔티티

각 컨텍스트의 "핵심 엔티티"는 설계 기준이며, 필드는 정책 확정 후 구체화한다.
🔸 표시는 [open-decisions.md](open-decisions.md)에 묶인 미결정 사항이다.

### 3.1 Auth — 인증/인가
**책임:** Google OAuth2 로그인(`@inha.ac.kr`만 허용), 학번·학년 검증(졸업생 차단), 성별 선택 입력, JWT 액세스 토큰 발급 및 리프레시 재발급, 관리자 권한 관리.

| 엔티티 | 책임 | 핵심 속성(설계 기준) |
|---|---|---|
| `User` | 서비스 사용자 | id, email(`@inha.ac.kr`), studentId(학번), 학년, **성별**, `Role`, createdAt, deletedAt(soft delete) |
| `RefreshToken` | 리프레시 토큰 보관/재발급 | id, userId, token, 만료시각 |

- 권한: `enum Role { USER, ADMIN }` (각각 `ROLE_USER`, `ROLE_ADMIN` 키 보유) + `@PreAuthorize`.
- 📌 현재 구현된 `User`는 email/studentId/role/createdAt/deletedAt만 보유한다. **정책상 필요한 성별·학년 필드는 아직 없음** → [open-decisions.md](open-decisions.md) "엔지니어링 정합성" 참조.

### 3.2 Profile — 프로필 및 성향
**책임:** 프로필 작성/수정/조회, 성향 정보(MBTI·관심사·연애스타일·흡연/음주 등) 관리.

| 엔티티 | 책임 | 핵심 속성(설계 기준) |
|---|---|---|
| `Profile` | 사용자 1인의 프로필 | id, userId, (🔸 사진), 자기소개, 연애스타일, 흡연/음주, MBTI 등 |
| `ProfileTag` | 관심사/태그(N개) | id, profileId, 태그 값 |

- 🔸 필수 입력 항목, 🔸 프로필 사진 공개 여부 미결정 → [open-decisions.md](open-decisions.md)
- 매칭의 공통 관심사 점수화는 `ProfileTag`를 입력으로 사용한다.

### 3.3 Matching — 매칭 시스템
**책임:** 매칭 요청(하루 1회), 하드/소프트 필터링, Spring Scheduler 기반 18:01 마감 → 저녁 일괄 매칭, MVP 규칙 기반 → 이후 Gemini Flash API 연동.

| 엔티티 | 책임 | 핵심 속성(설계 기준) |
|---|---|---|
| `MatchRequest` | "요청하기" 1건 | id, requesterId, 대상 정보, 요청일자(하루 1회 제약) |
| `MatchResult` | 매칭 성립/제안 결과 | id, 사용자쌍, 상태(제안/수락/성립), 매칭일자 |

- 하드 필터: 동성, 차단 상대, 기매칭 상대, 이미 요청(좋아요) 보낸 상대 제외.
- 소프트 필터: 🔸 최근 N일 활성 유저 우선 + 공통 관심사 점수화.
- 우선순위: ① 요청자끼리 → ② 조건 충족 시 미요청자에게 알림 제안.
- 🔸 매칭 실행 시각, 🔸 활성 유저 N일 미결정 → [open-decisions.md](open-decisions.md)

### 3.4 Chat — 실시간 채팅
**책임:** 채팅방 자동 생성, 실시간 메시지 송수신(WebSocket/STOMP), 알림(Firebase or SSE).

| 엔티티 | 책임 | 핵심 속성(설계 기준) |
|---|---|---|
| `ChatRoom` | 매칭된 2인의 방 | id, 참여자(2인), 생성시각, 종료/나감 여부 |
| `Message` | 채팅 메시지 | id, chatRoomId, senderId, 내용, 전송시각 |

- 채팅방은 매칭 성립 시 자동 생성. 한쪽이라도 나가면 방을 폐기하여 양쪽 모두 내용 확인 불가.
- 채팅방을 나가야만 다음 매칭/요청 가능.

### 3.5 Report — 신고/차단
**책임:** 신고 접수, 차단 처리 → 이후 매칭 영구 제외.

| 엔티티 | 책임 | 핵심 속성(설계 기준) |
|---|---|---|
| `Report` | 신고 1건 | id, reporterId, targetUserId, 사유, 신고시각 |
| `Block` | 차단 관계 | id, blockerId, blockedUserId, 차단시각 |

- 신고 → 자동으로 ①채팅방 나가기 ②상대 차단을 함께 수행.
- `Block`은 Matching의 하드 필터 입력으로 사용된다(영구 제외).

---

## 4. 설계 원칙 요약

1. 컨텍스트는 **자기 데이터만 소유**한다(엔티티는 한 컨텍스트에만 속한다).
2. 다른 컨텍스트 데이터가 필요하면 **ID로 참조**하거나 **인터페이스로 질의**한다.
3. 엔티티는 외부(컨트롤러 응답)로 직접 노출하지 않고 **DTO로 변환**한다([conventions.md](conventions.md)).
4. 위 엔티티 속성은 **설계 기준**이며, 🔸 미결정 항목이 확정되면 구체화한다.
