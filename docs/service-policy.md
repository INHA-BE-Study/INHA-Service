# 서비스 정책 (Service Policy)

인하대학교 재학생 전용 교내 소개팅 웹 서비스의 정책을 정의한다.
회원 / 매칭 / 프로필 / 채팅 / 신고·차단 5개 영역으로 나눈다.

> 🔸 표시는 **아직 결정되지 않은 항목**이다. 임의로 값을 정하지 말고 → **[open-decisions.md](open-decisions.md)** 를 따른다.

---

## 1. 회원 정책

### 1.1 가입 조건
| 항목 | 정책 |
|---|---|
| 인증 방식 | Google OAuth2 |
| 허용 계정 | **`@inha.ac.kr` 또는 `@inha.edu` 도메인 이메일만** 가입 가능 |
| 차단 | 그 외 도메인은 가입 거부 (현재 `CustomOAuth2UserService`에서 이메일 도메인 검증) |

### 1.2 재학생 검증
- 가입 시 **학번**과 **학년**을 사용자가 직접 입력한다.
- 입력 정보를 기준으로 **졸업생은 가입/이용을 차단**한다.
- 🔸 **대학원생 포함 여부 미결정** → [open-decisions.md](open-decisions.md)

### 1.3 성별 인증
- 회원가입 시 성별을 **사용자가 직접 선택**한다.
- 성별은 매칭의 하드 필터(이성 매칭)에 사용된다.

### 1.4 권한
- 권한은 `enum Role { USER, ADMIN }` 으로 구분한다.
- 관리자 기능은 `@PreAuthorize`로 보호한다.

## 2. 매칭 정책

### 2.1 기본 원칙
| 항목 | 정책 |
|---|---|
| 매칭 방식 | **1:1 단독 매칭** — 한 사람은 동시에 하나의 매칭만 가질 수 있다 |
| 매칭 중 제약 | **채팅방이 존재하는 동안에는 새 매칭이 발생하지 않는다** |
| 요청하기 | 하루 **1회**만 가능 |
| 요청 자격 | **채팅방이 없는 사람만** 요청 가능 |

### 2.2 매칭 타임라인 (매일)
| 시점 | 동작 |
|---|---|
| ~ 매일 18:01 | **요청하기 마감** (Spring Scheduler가 18:01에 마감 처리) |
| 🔸 저녁 (7시 or 8시 미결정) | 마감된 요청을 기준으로 **일괄 매칭 실행 → 결과 통지** |

- 🔸 **매칭 실행 시각(저녁 7시 / 8시) 미결정** → [open-decisions.md](open-decisions.md)

### 2.3 매칭 우선순위
1. **1순위:** "요청하기"를 누른 사람들끼리 우선 매칭한다.
2. **2순위:** 조건을 만족하는 경우, "요청하기"를 누르지 않은(미요청) 대상에게 **알림**을 보내 매칭을 제안한다.

### 2.4 매칭 확정
- 제안된 상대가 **수락**해야 **최종 매칭**이 성립한다.
- 최종 매칭이 성립하면 채팅방이 자동 생성된다(§4 참조).

### 2.5 필터링 규칙
- **하드 필터(반드시 제외):** 동성, 차단한/차단당한 상대, 이미 매칭된 상대, 이미 "요청하기(좋아요)"를 보낸 상대.
- **소프트 필터(점수화):** 🔸 최근 N일 이내 로그인한 **활성 유저** 우선, 공통 관심사 기반 점수화.
- 🔸 **활성 유저 기준 N일 미결정** → [open-decisions.md](open-decisions.md)
- 매칭 로직은 **MVP에서는 규칙 기반**, 이후 **Gemini Flash API** 연동으로 고도화한다.

## 3. 프로필 정책

| 항목 | 정책 |
|---|---|
| 선택 입력 | MBTI, 관심사, 연애스타일, 흡연/음주 여부 등 (성향 정보) |
| 필수 입력 | 🔸 **미결정** → [open-decisions.md](open-decisions.md) |
| 프로필 사진 공개 | 🔸 **미결정** → [open-decisions.md](open-decisions.md) |

- 프로필 성향 정보는 매칭의 소프트 필터(공통 관심사 점수화)에 활용된다.

## 4. 채팅 정책

| 항목 | 정책 |
|---|---|
| 채팅방 생성 | 최종 매칭이 성립하면 **자동 생성** |
| 동시 채팅 수 | 1개 (1:1 매칭 원칙과 동일) |
| 새 매칭 조건 | **현재 채팅방에서 나가야만** 다음 매칭/요청이 가능 |
| 채팅방 나가기 효과 | 나가면 **양쪽 모두 대화 내용을 더 이상 확인할 수 없다** (방 폐기) |
| 나가는 방법 | ① 직접 나가기, ② **신고 시 자동 나가기** |
| 실시간 전송 | WebSocket(STOMP) 기반 |
| 알림 | Firebase 또는 SSE (수단 검토 중 — [architecture.md](architecture.md) 참조) |

## 5. 신고 / 차단 정책

| 항목 | 정책 |
|---|---|
| 신고 시 처리 | **자동으로 채팅방 나가기 + 상대방 차단**을 함께 수행 |
| 차단 효과 | 차단한 상대는 **이후 매칭에서 영구 제외** (하드 필터) |
| 채팅 내용 | 채팅방을 나가므로 양쪽 모두 대화 내용 확인 불가 |
